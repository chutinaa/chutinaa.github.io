⑤ 技术实现 演示版 / 生产版分别说明

本演示页纯浏览器 JavaScript，单文件 HTML，零依赖、零网络请求。演示不真的跑 OCR：扫描件那一栏的文本是预置的虚构识别结果（含刻意保留的 O/0、I/1 误读），用来展示判定口径的差别。
运行环境生产版：Bun 起本地 HTTP 服务 + 浏览器单页前端，双击 bat 启动，全部相对路径，可整包拷给同事。
Word 直读自写 zip 中央目录解析 + zlib.inflateRaw 解压 word/document.xml 及全部页眉页脚，取原生字符，3–8 ms、零识别误差。不依赖 Office，也不走 PowerShell（避开编码坑）。
PDF / 扫描件先用 Scribe.js 把 PDF 栅格化成 PNG（Windows 没有可脚本调用的 PDF 渲染器），只用它栅格化，不用它 OCR。
OCR 引擎Windows 系统内置 OCR（Windows.Media.Ocr），通过 PowerShell + WinRT 反射调用（System.Runtime.WindowsRuntime 拿 AsTask 转同步）。完全离线、免安装、不需要管理员权限、零成本，约 0.5–0.6 秒/页，已装 en-US 与 zh-Hans-CN 语言包。
比对算法按行压掉全部非字母数字后做容错子串搜索（OCR 会往编号中间插逗号空格，不能用正则切候选）；只收 5 组字形真分不开的等价：0/O/D 1/I/L/T 2/Z 5/S 8/B，其余差异一律计分，宁可多几行「需人工」也不出一次假匹配。
回归基线真实数据 86 个编号 → 76 匹配 / 8 需人工 / 2 未找到；5,000 个随机编号假阳性 0%。
为什么不用云端 LLM，也不用 Tesseract：文档含机密信息，没有合规通道外发给外部模型，本地方案是唯一可行的选择；审核场景要求判定可复现、可审计，LLM 的非确定性输出天然不适合。Tesseract / Scribe.js 实测 4 页 53 秒，系统内置 OCR 只要 2.3 秒，且前者的 WASM + Worker 必须架 HTTP 服务器才能跑。
判定口径：Word 直读 = 文本可信，只有逐字一致才算通过，差一个字符归「需人工」；OCR = 机器读可能认错，O/0、I/1 等常见混淆自动容错，其他差异仍归「需人工」。 Demo · 单文件 HTML · 离线可用
