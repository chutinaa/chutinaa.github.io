Tool Inventory

Multi-Source Data ReconciliationCompares exports from two systems row by row on key fields and tiers the results with recommended actions
ProductionTutorialExcel + CSV input
▶
InputExcel export from the business system + CSV export from the data warehouseOutputRow-level comparison + upload file built from selected rows

Problem

  • Records had to be confirmed consistent across two systems before approval. Manually VLOOKUP-ing four fields across a 200-row batch took half a day.

Key mechanics

  • Four fields are compared: entity ID, customer, region, type. Only a conflict in the entity ID is called an ID conflict (the two systems are talking about different objects); differences in the other three are attribute discrepancies (same object, attributes filled in differently). They follow different handling paths and the terms are never mixed.
  • The status field carries one dimension only (entity ID); attribute discrepancies are separate boolean flags. Rows are sorted by handling tier rather than alphabetically, so the rows needing action come first and voided rows always sink to the bottom.
  • Only clean rows are pre-selected; any row with an attribute discrepancy must be confirmed by hand before it enters the export.
  • The CSV parser handles quoted commas, so customer names containing commas no longer shift entire rows.
Safeguard: rows missing required supporting material are excluded from export by default and flagged with a black-bordered tag. When one request contains a serious issue, the clean rows in the same group are also deselected, so a batch is never uploaded half-complete.
Batch Record FormatterPaste a whole system page; the tool extracts fields, detects the operation type, reconciles counts and exports by region
ProductionTutorialPaste / Excel input
▶
InputRaw text pasted from a system page, or an Excel file read by column nameOutputUpload files grouped by region

Problem

  • Dozens of requests a day were copied one by one from a web page into a template, in inconsistent formats (tabs, pipes and spaces all mixed together).

Key mechanics

  • Fields are extracted by pattern, not by column position: ticket number, 9–13 digit account ID, site code.
  • The operation type (lock / unlock / change site) is detected by keyword frequency. If more than one type appears, the tool asks the user to split the batch instead of guessing.
  • Excel input is matched by column name (exact match first, then partial match with exclusion words), never by column order.
Safeguard: the record count declared on the page is reconciled against the parsed count. Any gap raises a yellow banner and points to the likely skipped row (a line with a ticket number but missing other fields). Better to warn once too often than to silently drop a record.
Request-to-Record VerificationCross-checks the IDs on a request form against system records, one by one, and highlights differences
ProductionTutorialTwo-table input
▶
InputTicket export from the system + spreadsheet submitted by the requesterOutputItem-level verification result, usable directly as the review note

Problem

  • Approval requires confirming that the request form and the system record refer to the same set of entities. One missed item means one round of rework.

Key mechanics

  • IDs are normalized first (case, whitespace, hyphens) to remove formatting noise before comparison, reducing false alarms.
  • Results use three colors: match / needs manual confirmation / not found in system, with each item stating exactly where it differs.
Safeguard: if the two tables have different row counts, the tool warns first rather than producing a verdict. IDs not found are listed as a separate group so they are never buried among ID conflicts.
Cross-Site Field ConverterBulk-edits site fields and splits the result into one upload file per target platform
ProductionTutorialMulti-platform output
▶
InputList of records to be modifiedOutputMultiple upload files, split by platform

Problem

  • Each platform has its own upload template, so one batch of changes had to be split into several files by hand and reformatted for each.

Key mechanics

  • Original columns are preserved; derived values go into new columns, never overwriting the source, so every change can be traced back.
  • Records are grouped automatically by platform rules, one file per group, with the platform and date in the file name.
Safeguard: the total row count after grouping must equal the input row count. If it does not, the export is refused and the tool reports which group is off.
Document Compliance CheckReads Word files natively, falls back to OCR for scans, and verifies declaration documents field by field
StandaloneCase 02 flagship
▶
InputSystem records + submitted Word / PDF / image filesOutputField-level verification result + one-click review conclusion

Key mechanics

  • Native text is extracted first based on file type (Word is read directly from its zip structure); OCR is only the fallback. The two sources carry different confidence levels, so the matching rule and the wording of the verdict switch accordingly, using a single algorithm with one flag.
  • Everything runs locally using the operating system's built-in OCR, with no cloud dependency.

Hub and Shared Design Principles

Entry pointOne Hub page lists every tool in two groups, "frequent" and "other". Each card links to both the production and tutorial editions, and the footer states "N tools · all work offline".
Form factorEach tool is a single .html file that opens on double-click. Spreadsheet library, styles and icons are all embedded, so it works even when the corporate network blocks the internet.
Tutorial editionSame source code as production, with one switch that adds an explanation layer and sample data. Logic is changed in one place and both editions stay in sync.
TerminologyEvery status word means exactly one thing (for example "ID conflict" refers only to a primary-key conflict; attribute differences have their own name). Before changing any wording, grep the full test suite and separate assertion descriptions from decision criteria.
SafeguardsEvery tool has one reconciliation identity (record count, row count or total). If it fails, the tool blocks; it never lets the gap pass quietly.
VerificationRegression runs in a headless browser. Any change to wording or metric definitions is tested before delivery, with a backup, byte count and fingerprint comparison attached.
Why HTML instead of scripts or plugins: team members have no admin rights, cannot install software, and should not have to configure an environment just to use a tool. A single file opens for anyone on double-click and works the same when copied to another machine. Technology choices follow the usage context. That is the one decision behind these six tools that never changed.
